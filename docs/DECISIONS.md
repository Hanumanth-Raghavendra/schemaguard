# Architecture decisions

One entry per decision, newest last. A decision is changed only by adding a new entry that supersedes it.

| ID | Date | Decision | Why |
| --- | --- | --- | --- |
| D-001 | 2026-11-12 | PostgreSQL DDL only for 1.0 | Dialects differ too much to do several well; Postgres lock behaviour is the best documented |
| D-002 | 2026-11-12 | One repository, Maven multi-module: `engine`, later `api`, `cli`; `web` and `action` alongside | The engine is reused by three products and must stay free of framework code |
| D-003 | 2026-11-12 | `engine` has zero runtime dependencies | Testable without Spring, tiny CLI jar, nothing to break on upgrade |
| D-004 | 2026-11-12 | Hand-written lexer and recursive-descent parser instead of a parsing library | Full control over `ALTER` coverage and error positions; unsupported input is reported, not guessed at |
| D-005 | 2026-11-12 | The lexer emits `WORD` and does not classify keywords | Most PostgreSQL keywords are non-reserved, so only the parser has the context to decide |
| D-006 | 2026-11-12 | The engine never throws on bad SQL; it returns diagnostics with source spans | One error must not hide the rest of a large dump; the UI needs line and column |
| D-007 | 2026-11-12 | No license file yet (all rights reserved by default) | Open source vs source-available affects the income path; decide before 1.0 |
| D-008 | 2026-11-12 | Java 21, JUnit 6.1.3, AssertJ 3.27.7, JaCoCo 0.8.16; line-coverage gate of 85% on `engine` | Versions checked against Maven Central on this date; the gate keeps the engine honest |
| D-009 | 2026-11-12 | Base package `io.github.hanumanthraghavendra.schemaguard`, groupId `io.github.hanumanth-raghavendra` | The reverse-domain namespace the author actually controls, valid for Maven Central later |
| D-010 | 2026-11-12 | The parser returns a list of `Statement`s; a separate `CatalogBuilder` (1.5) turns them into a schema | Rules need the statements themselves ("this ALTER rewrites the table"); diff needs the resulting schema. One parser serves both |
| D-011 | 2026-11-12 | Expressions are stored as canonical text, not as a syntax tree | The engine only compares and prints expressions. A full expression grammar would be most of the SQL language for no benefit to version 1.0 |
| D-012 | 2026-11-12 | Type names are canonicalised at parse time (`int4` -> `integer`, `varchar` -> `character varying`, `char` -> `character(1)`); unqualified user types keep a null schema until the catalog resolves them | Stops alias spellings showing up as false differences; the parser alone cannot know whether `status_t` is built in |
| D-013 | 2026-11-12 | Column-level constraints are lifted into table-level constraints over one column; primary-key and identity columns are marked NOT NULL | One shape for later stages, and it matches what PostgreSQL stores in its catalog |
| D-014 | 2026-11-12 | Parser errors use an internal exception caught once per statement; the public API never throws | Keeps the recursive-descent methods free of error plumbing while preserving D-006 |
| D-015 | 2026-11-12 | Statements are split on every semicolon, except inside `BEGIN ATOMIC ... END` and `CREATE RULE ... DO (...)` | Splitting on parenthesis depth would let one missing `)` swallow the rest of the file |
| D-016 | 2026-11-13 | The parser is split into `ParserBase` (cursor + shared grammar fragments), `TableElementParser` (columns and constraints) and one class per statement family (`IndexParser`, `SequenceParser`, `AlterTableParser`), all sharing one `TokenCursor` | Each file holds one grammar. `ALTER TABLE ... ADD` reuses the exact column and constraint code of `CREATE TABLE`, so the two cannot drift apart |
| D-017 | 2026-11-13 | `ALTER TABLE` is kept as a list of sealed `AlterAction` records; the parser does not apply them | The action is what carries the risk (lock level, table rewrite). The catalog (1.5) applies actions; the rules engine (phase 3) judges them |
| D-018 | 2026-11-13 | Index keys always store sort order and NULLs order with defaults filled in; sequences leave unspecified start, min and max empty | Index defaults are fixed, so filling them in makes equal indexes compare equal. Sequence defaults depend on type and direction, so the catalog resolves them |
| D-019 | 2026-11-13 | An `ALTER TABLE` containing any unmodelled action is reported as unsupported as a whole | A half-understood statement would produce a falsely reassuring risk report |
| D-020 | 2026-11-13 | `CatalogBuilder` applies each statement atomically: state is copied before a statement and restored if any part of it fails | PostgreSQL does the same. A half-applied `ALTER TABLE` would produce a schema no server could be in |
| D-021 | 2026-11-13 | Catalog errors reuse PostgreSQL's own message text, with SchemaGuard codes (`SG-CAT-001` to `006`) | Familiar and searchable for users; and it lets a script run the whole error table against a real server to check it |
| D-022 | 2026-11-13 | Unnamed constraints, indexes and serial sequences get the names PostgreSQL would generate (`NameGenerator`), including its shortening and numbering rules | A script and its dump must build equal catalogs, or every unnamed object would show up as a difference |
| D-023 | 2026-11-13 | Correctness is established by oracle tests: fixtures hold a script and the `pg_dump` of a real PostgreSQL 16 that ran it; the two must build equal catalogs | The server is the specification. Hand-written expectations only encode what the author believes |
| D-024 | 2026-11-13 | Expressions are compared through `Expressions.fingerprint` (parentheses and casts removed) where exact text differs | PostgreSQL prints `total >= 0` as `(total >= (0)::numeric)`. The fingerprint separates "printed differently" from "changed" without a full expression parser. It is a hint, never a proof |
| D-025 | 2026-11-13 | A catalog stores resolved values: sequence start/min/max, foreign-key target columns, qualified enum types, canonical `nextval` defaults, constraints in name order | Two ways of writing the same schema must give equal catalogs (`Catalog` is a record, so that is plain `equals`) |
| D-026 | 2026-11-14 | `SqlWriter` writes model objects as DDL and a catalog as a pg_dump-ordered script (types, sequences, tables with valid checks, NOT VALID checks, keys, indexes, foreign keys, ownership) | One writer for the diff's output and the phase 4 planner. Its correctness is checked twice: the parser reads every script back to an equal catalog, and PostgreSQL 16 loads it and dumps it to an identical catalog |
| D-027 | 2026-11-14 | The diff is literal: every object-level difference is listed, including ones implied by another (indexes of a dropped table) | Nothing can go missing. Knowing that `DROP TABLE` takes its indexes with it is the planner's job, not the diff's |
| D-028 | 2026-11-14 | Constraints and indexes left over after matching by name are matched by definition; an equal definition under a new name is a rename | An index or constraint is fully described by its definition, so this is certain, not a guess |
| D-029 | 2026-11-14 | Tables, columns and enum values are never declared renamed. The diff reports the drop, the add, and a `RenameCandidate` with a confidence and the evidence for it | Two objects with the same definition may still hold different data. Calling it a rename wrongly would plan a migration that keeps the wrong data; the user decides |
| D-030 | 2026-11-14 | Candidate confidence: columns 0.7 x name similarity + 0.3 if in the same position; tables 0.5 + 0.5 x similarity (columns must be identical); enum values 0.5 + 0.5 x similarity (must take the removed value's place). Name similarity is the best of edit distance, word containment (0.8) and abbreviation (0.6). Below 0.5 nothing is reported; each name is in at most one candidate | Simple enough to explain line by line. Position is strong evidence because PostgreSQL appends added columns at the end, so a renamed column keeps its place |
| D-031 | 2026-11-14 | A change is `cosmetic` when the two expressions have equal fingerprints. `SchemaDiff.significant()` drops cosmetic changes; nothing is ever dropped from `changes()` | Comparing a hand-written script with a dump would otherwise be all noise, but a fingerprint is a hint, not a proof (D-024) |
| D-032 | 2026-11-14 | Golden files for whole-diff output (`expected-diff.txt`), rewritten only with `-Dgolden.update=true` and reviewed in the commit diff | A change in output becomes a visible, reviewable diff instead of a silently updated assertion |
| D-033 | 2026-11-14 | Lock, rewrite and scan facts are measured on a real server by `scripts/measure-locks.sh` and stored as fixtures; `Operation`, `LockLevel` and `TypeChange` are tested against them | Lock behaviour is the product's core claim and the kind of fact people remember wrongly. Measuring caught three things memory had wrong: `NOT VALID` is ignored inside `CREATE TABLE`, `txid_current()` is stable, and `VALIDATE` of a foreign key takes ROW SHARE on the referenced table. A new PostgreSQL version is supported by re-running the script |
| D-034 | 2026-11-14 | A scan is detected through `pg_stat_xact_user_tables` (scan counters inside the transaction), a rewrite through `pg_relation_filenode`, a lock through `pg_locks` before `ROLLBACK` | All three are read from the server's own bookkeeping in the same transaction as the statement, so nothing is inferred |
| D-035 | 2026-11-14 | The report judges the direct route: one plain statement per change (`DirectRoute`) | The input is two schemas, not a script, and the direct route is the migration people write first. Judging a user's own script statement by statement is planned with the planner (phase 4) |
| D-036 | 2026-11-14 | One class per rule (Strategy), stateless, registered in `RuleRegistry`; metadata in a `RuleInfo` record; ids `SG-R1xx` locking, `2xx` rewrite, `3xx` data loss, `4xx` can fail, `5xx` compatibility, never reused | A rule can be read, tested, documented and switched off alone. Stable ids let users disable a rule in a config file and link to its documentation |
| D-037 | 2026-11-14 | Rules see both catalogs through `RuleContext`; a change to a table created in the same diff produces no finding | A new table is empty: nothing done to it is slow or loses data. Without this the tool would warn about every `CREATE TABLE` with a foreign key, and tools that cry wolf get ignored |
| D-038 | 2026-11-14 | Severity weights LOW 10, MEDIUM 30, HIGH 60, CRITICAL 85; a finding's score is weight x certainty; the diff score is the noisy-OR `100 x (1 - prod(1 - s_i/100))`; bands 1-24 LOW, 25-49 MEDIUM, 50-74 HIGH, 75+ CRITICAL | One finding alone scores inside its own band, every further finding raises the total, many small risks add up, and the total cannot pass 100. A sum would need a cap and a maximum would ignore everything but the worst finding |
| D-039 | 2026-11-14 | CRITICAL is reserved for irreversible data loss (drop table, drop column); blocking and rewriting are HIGH | A blocked table recovers when the statement ends; dropped data does not come back |
| D-040 | 2026-11-14 | Findings that rest on a guess carry a certainty below 1: a rename candidate uses its confidence, an unknown function's default uses 0.5 | The report can mention an uncertain risk without letting it weigh as much as a certain one |
| D-041 | 2026-11-14 | The lock-timeout advice (`SG-R111`) is one finding per migration, naming the tables, not one per statement | It applies to nearly every `ALTER TABLE`; repeated per change it would bury the findings that differ |
| D-042 | 2026-11-14 | Function volatility comes from a resource file listing all 2,633 built-in functions of PostgreSQL 16, taken from `pg_proc` | A default such as `lower('X')` must not raise a rewrite warning, and a user function must not be assumed safe. Only a full list separates "known stable" from "unknown" |
| D-043 | 2026-11-14 | `docs/RULES.md` is generated from the rule classes and guarded by a test | Documentation written by hand next to 38 rules would be wrong within a month |
| D-044 | 2026-11-15 | The planner sorts statements into fixed stages (types, sequences, drop foreign keys, drop tables, drop constraints, drop indexes, renames, create tables, columns, drop columns, keys, foreign keys, indexes, validate, swap, sequence options, drop sequences, drop types) instead of solving a dependency graph | Schema objects depend on each other in a small, known number of ways, so a fixed order is enough, easy to read and deterministic. The one true cycle, tables that reference each other, is dropped in one statement |
| D-045 | 2026-11-15 | A plan is proven by running it: old schema + plan on a real PostgreSQL 16, `pg_dump`, and the dump must build the same catalog as the dump of the new schema. 264 plans, locally and in CI (postgres:16 service container; no Testcontainers, the build machine has no Docker) | Generated SQL that only looks right is worthless. The first run refused 4 of 214 plans and found two real ordering bugs (a sequence dropped with its old owner, an identity's hidden sequence taking a name) |
| D-046 | 2026-11-15 | The safe route replaces a statement only where the table can have rows; on a table the migration creates, the plain statement stays | The safe variants cost extra statements and cannot run in a transaction. On an empty table they buy nothing |
| D-047 | 2026-11-15 | A confirmed rename is applied to the old catalog (by running `RENAME` through `CatalogBuilder`), and the rest is planned from the diff of that catalog | Reuses the catalog's knowledge of what a rename does to constraints, indexes and sequences, and what follows from it (index names that now differ) falls out of the ordinary diff |
| D-048 | 2026-11-15 | The safe route never hides a risk it cannot remove: the step keeps a caution with the rule that still applies, and changes with no statement at all are listed as not planned | A "safe plan" that silently contains a table rewrite would be worse than no plan |
| D-049 | 2026-11-15 | A changed key is swapped in one statement (`DROP CONSTRAINT x, ADD CONSTRAINT x ... USING INDEX x_new`); a changed CHECK or foreign key is added under a temporary name, validated, then swapped by drop and rename | The table is never without the rule, and the long work (index build, validation) happens under locks that let writes through |
| D-050 | 2026-11-15 | The linter applies each statement (each action of a multi-action `ALTER TABLE`) to the catalog as it is at that point, diffs before/after, runs the ordinary rules on that one-step diff, and keeps a lock finding only if the statement is the kind of statement the finding is about | One set of rules serves both inputs. The exact statement (CONCURRENTLY, USING INDEX, NOT VALID) decides the lock, so a safe script is not blamed for the plain variant |
| D-051 | 2026-11-15 | Tables a script creates are passed to the rules as known-empty (`RuleContext(diff, emptyTables)`) | Nothing done to an empty table is slow or loses data, however many statements later it happens |
| D-052 | 2026-11-15 | Compatibility findings that a later statement mends (`SG-R501`, `SG-R503`, `SG-R506`) are judged once at the end of the script against the full before/after diff | The safe NOT NULL route drops its helper CHECK; a dropped default is followed by an identity. Reporting those would make the planner's own output look dangerous |
| D-053 | 2026-11-15 | Two rules exist only for scripts: `SG-R403` CONCURRENTLY inside a transaction block, `SG-R510` rename in one step. They live in `ScriptRules`, not in the registry, and are documented with the others | Two schemas cannot show either; a script can |
| D-054 | 2026-11-15 | Linter, rules and planner are tested against each other: linting the direct plan for each rule case must find exactly what the rules find in the diff; linting the safe plan must find none of the risks the safe route claims to remove | Three components that describe the same risks in three ways would drift apart without a test that binds them |
| D-055 | 2026-11-16 | The differ skips tables that are equal, and the catalog keeps an unchanged table as the same object | The linter diffs the whole schema once per statement; this made it 4x faster (800 statements on 400 tables: 5.3 s to 1.3 s) without a second code path. A test guards the object identity |
| D-056 | 2026-11-16 | A seeded fuzz test (1,500 broken scripts through every stage) is part of the build | The engine will sit behind a public API: any input must give an answer, never an exception. 60,000 cases found no crash before the test was added |
| D-057 | 2026-11-17 | The API is a separate Maven module that imports the Spring Boot BOM itself; the parent POM stays framework-free | The engine must never depend on Spring. Importing the BOM only in `api` keeps the engine's dependency tree empty and lets the API move to a new Boot version alone |
| D-058 | 2026-11-17 | The API has its own response records; engine records never reach JSON | The engine can rename or reshape a record without breaking clients. The mapping lives in one class (`DtoMapper`) |
| D-059 | 2026-11-17 | A schema with any ERROR diagnostic is refused with 422 and the diagnostics (input, line, column); WARNINGs (skipped statements such as views) come back next to the result | A result built on a schema the parser misread would be confidently wrong. A view the engine does not model is no reason to refuse the rest |
| D-060 | 2026-11-17 | Limits: 3 MB body (checked before parsing, also for chunked bodies), 1 M characters per SQL input, 2,000 statements per linted script; 413 beyond | Linting cost grows with schema size times script length; the limits keep one request well under a second on the free tier |
| D-061 | 2026-11-17 | Errors are RFC 9457 problem documents with a stable `code` (`SG-API-4xx`); a 500 never carries the exception message, and request bodies are never logged | One error format for clients. Schemas can be confidential, so nothing of them may leak into logs or error bodies |
| D-062 | 2026-11-17 | Renames are a polymorphic JSON type (`kind`: table, column, enumValue), the same shape in the diff's rename candidates and in the plan request | A client confirms a rename by sending back exactly what the diff gave it |
| D-063 | 2026-11-17 | Deploy as a Docker image on Render's free tier, described by `render.yaml`; CI builds the image, starts it and calls it on every push | Free, reproducible, and the same image runs anywhere. CI proves the image works, since the development machine has no Docker |
| D-064 | 2026-11-17 | Persistence is optional and wired by hand (`PersistenceConfig`, plain spring-jdbc + HikariCP + Flyway), not through Spring Boot's JDBC and Flyway auto-configuration | Boot 4 ships those as separate modules; leaving them out means no DataSource is required to start. Without `SCHEMAGUARD_PERSISTENCE_URL` the service runs as before and permalinks answer 503 |
| D-065 | 2026-11-17 | Nothing touches the database at startup: the pool connects on first use (`initializationFailTimeout = -1`), Flyway migrates on the first permalink request and retries on the next if it failed; health checks never query it; Render probes liveness only | A sleeping, down or misconfigured free-tier database must cost the permalinks a 503, never the whole service, and health probes every few seconds must not keep Neon awake (its free tier counts compute hours) |
| D-066 | 2026-11-17 | Saved request and result are stored as `json`, not `jsonb`, together with the engine version | They are never queried inside; `json` keeps the text byte for byte, so a permalink shows exactly what was computed even after the engine changes |
| D-067 | 2026-11-17 | Ids are 128 random bits in base 62 (22 characters); deletion needs a 256-bit token returned once at save time, of which only the SHA-256 is stored; a malformed id is answered 404 without a query | The id is the only protection of a shared analysis, so it must be unguessable. A leaked database does not allow deleting anything |
| D-068 | 2026-11-17 | Saving runs the analysis first and stores nothing if it fails; limits of 1 MB per analysis and 200 MB in total (507 Insufficient Storage beyond); 30-day retention by an hourly job, and expired rows are invisible before the job runs | Bounded storage on a free tier without accounts. Results are larger than requests (a lint result is ~8x its input), so the limit counts both |
| D-069 | 2026-11-17 | The database URL accepts a libpq string (`postgresql://user:pass@host/db?sslmode=require`) as well as JDBC; libpq-only parameters such as `channel_binding` are dropped; the URL is never logged with its password | Neon and most hosts hand out the libpq form; pasting it as it is removes a common deployment mistake |
| D-070 | 2026-11-17 | The service runs in UTC (`TimeZone.setDefault` in `main`, `-Duser.timezone=UTC` for tests) and the build keeps parameter names (`-parameters`) | pgjdbc sends the JVM zone at login, and servers without legacy zone data refuse old names such as Asia/Calcutta. Spring needs parameter names for `@PathVariable`; Boot's own parent POM sets the flag, ours did not, and the tests caught both |
| D-071 | 2026-11-17 | SchemaGuard lints its own Flyway migrations in a test (`OwnMigrationsTest`): each migration against the schema of the ones before it, nothing above LOW allowed | The product's promise applied to itself: a migration that locks or rewrites the analysis table fails the build |
| D-072 | 2026-11-18 | The deployed service is checked by a manual workflow (`live-smoke.yml`) that calls it as a client would: health, OpenAPI, rules, every analysis, a refused schema, the full save/open/delete round trip with a wrong token, and a CORS preflight. Saved analyses must work by default | CI proves the image works on a runner; only a call to the real service proves the deploy (Render settings, the Neon secret, CORS) works. Manual, because a scheduled call every few hours would keep the free service and the database awake |
| D-073 | 2026-11-18 | Render deploys a push only after its GitHub checks pass (`autoDeployTrigger: checksPass`) and only when the push changes a path the Dockerfile copies (`buildFilter`) | The image build skips the tests, so a commit with failing tests used to go live. Docs and web-only pushes would otherwise rebuild and restart the API and spend the free build minutes |
| D-074 | 2026-11-18 | The OpenAPI document states the response contract exactly: every field of a response record is required, fields that can be null carry jspecify `@Nullable` and become `type: [..., "null"]`, and the rename subtypes are flattened into a plain discriminated union. `OpenApiContractTest` keeps a copy in `web/openapi.json`; the web app's types are generated from it | Jackson writes every field, nulls included, so "optional" in the document was false and would have made the UI guard against holes that never occur. springdoc's `allOf` back-reference from each subtype to its parent made generated clients collapse renames to `any`. A copied contract that fails the build on drift is how a UI in another language stays in step with the API |
| D-075 | 2026-11-18 | Web stack: Vite 8, React 19, TypeScript 5.9, Tailwind 4, `openapi-fetch` for a typed client, Monaco bundled from npm and loaded on demand, fonts self-hosted from Fontsource. No router until a second page exists (6.2) | Newest versions whose peer ranges agree: typescript-eslint supports TypeScript below 6.1 and openapi-typescript asks for 5.x, so 5.9 rather than 6 or 7. Monaco's default loader fetches from a CDN; bundling keeps the app working without third parties. The editor chunk is 2.7 MB, so it loads after the page and a plain text area works meanwhile |
| D-076 | 2026-11-18 | Every lock is drawn on PostgreSQL's eight-step lock scale (ACCESS SHARE to ACCESS EXCLUSIVE), coloured by what ordinary traffic does: calm while reads and writes continue, amber when writes wait, red when everything waits. Findings are sorted by score; labels use plain words ("Compare two schemas", "Check a migration", Risks, Changes, Plan) | The lock is the fact a reviewer acts on, and its position on the scale shows at a glance how bad it is; the colour carries the meaning, not decoration. The API returns findings in plan order, which buries the worst one |
| D-077 | 2026-11-18 | The page pings `/actuator/health/liveness` (no-cors) as it loads, and a request still pending after 3 seconds shows a notice that the server is starting | The free Render instance sleeps after 15 idle minutes and takes about a minute to wake. Starting it while the person is still typing hides most of that; telling them why it is slow beats a spinner |
| D-078 | 2026-11-19 | Sharing saves one analysis per page: the risk report for "Compare two schemas", the lint for "Check a migration". The link page shows what was saved and offers "Open in the editor", which runs the full analysis again on the saved inputs. The delete key stays in the sharer's localStorage; deleting asks for an inline confirmation | One saved result per link keeps the stored record small and matches the API's kinds. Changes and plan are cheap to recompute and deterministic, so storing them as well would only add rows. A browser dialog for the confirmation would block the page and is hard to test |
| D-079 | 2026-11-19 | A confirmed rename is judged by linting the generated plan ("Check this plan as a migration") instead of adding renames to `/api/v1/report` | The linter already judges `RENAME COLUMN` (SG-R510) and sees that no data is dropped, so the plan's real risks need no new API. Renames on `/report` would need the planner's rename step inside the rule engine |
| D-080 | 2026-11-19 | Markdown export is built in the browser from the responses; JSON export is the inputs plus every response as received | The API already returns everything needed; a server-side Markdown endpoint would duplicate the formatting and cost a round trip on a free host that may be asleep |
| D-081 | 2026-11-20 | The ER model is computed in the engine (`diagram.ErModel`) from the two catalogs, with every mark taken from the diff's significant changes, and served by `POST /api/v1/model` | Marks from the diff agree with the change list by construction: a respelled type is unchanged, a possible rename is a drop and an add until confirmed. In the engine it is plain Java with unit tests, usable later by the CLI |
| D-082 | 2026-11-20 | The diagram is hand-drawn SVG positioned by dagre (layered layout, referenced tables first); pan by drag, zoom by Ctrl or Cmd with the wheel, buttons or keys; it loads as its own chunk | dagre only places boxes (19 kB gzipped with the drawing code), so the look stays ours and every mark carries a word as well as a colour. A plain wheel keeps scrolling the page; trapping it inside a diagram is a common annoyance |
| D-083 | 2026-11-20 | The example gallery replaces "Load an example" in compare mode: seven real scenarios, each run through the API before it was added, and one click fills the editors and runs the analysis | The Blueprint asks that a recruiter sees results in one click. Checking each scenario against the API keeps the gallery honest: the rename example uses names the diff recognises (86%), not ones it would miss |
| D-084 | 2026-11-20 | The web app is a Vercel project linked to the repository (root `web/`), built with the settings pinned in `web/vercel.json`, at https://schemaguard-v1.vercel.app. Only that origin and `http://localhost:5173` may call the API from a browser | Git-linked deploys need no tokens in CI. Pinned settings keep the build in the repository rather than in a dashboard. Preview deployments get other addresses and stay blocked by CORS on purpose: they are for looking at the UI, not for writing to the shared database |
| D-085 | 2026-11-20 | The same Playwright test runs in CI against a local API and PostgreSQL, and in the live smoke workflow against the deployed site | One script states what "works" means (analyse, share, open, delete). Running it live catches what no local run can: Vercel settings, the CORS value on Render, and the real database |
| D-086 | 2026-11-20 | The web app is served with a Content-Security-Policy (scripts, workers and fonts from its own origin only; network calls to itself and the API; styles may be inline because Monaco and React set them; no framing), `nosniff`, a strict referrer policy and a permissions policy, plus a year of caching for the hashed files in `/assets/`. A lazily loaded part sits behind an error boundary | The app renders other people's SQL, so script injection must have nowhere to go. The policy was tested by running the end-to-end test under it, and that test now fails on any blocked resource. Monaco is 700 kB gzipped; immutable caching makes the second visit instant. Without a boundary, one failed chunk download unmounted the whole page |
| D-087 | 2026-11-20 | `main` carries the release version (0.5.0) at the moment it is tagged, then moves to the next `-SNAPSHOT`; `CHANGELOG.md` records each release | Shared links and the API's build info show the engine version; they must say 0.5.0 for the release, and a build made after it must not. A changelog gives the GitHub release its notes |
| D-088 | 2026-11-20 | Dependabot opens grouped minor and patch updates monthly for Maven, npm, GitHub Actions and Docker; majors one by one; TypeScript majors and Playwright are ignored | CI (tests, coverage gates, real PostgreSQL, end to end) decides whether an update is safe, so updates are cheap to take and should not pile up. Monthly and grouped keeps the noise to a few pull requests. TypeScript majors break the lint and codegen tools (D-075); Playwright must match the build container's browsers |
| D-089 | 2026-11-22 | The web app's address is https://schemaguard-v1.vercel.app (the owner renamed it from schemaguard-nu, which Vercel had picked because `schemaguard` was taken). Every reference moved with it: CORS in `render.yaml`, canonical and preview tags and the preview image, the live smoke test's defaults, and the docs | The old address no longer serves the app, so leaving it anywhere would break CORS or send people to a dead link. The address appears in one place per concern, so a rename is a search and a check |
| D-090 | 2026-11-22 | The web app calls the API on its own origin: Vercel rewrites `/api/*` to the Render API (rewrite caching off), and Vite's dev and preview servers forward `/api` the same way. The API keeps its CORS list, which must include the Vercel origin because the rewrite forwards the browser's `Origin` header, plus the local dev and preview origins | Phase 7 adds login with an httpOnly refresh cookie. Set by onrender.com for a page on vercel.app, that cookie would be third-party and blocked by more and more browsers; through the rewrite it is first-party.
